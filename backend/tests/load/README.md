# Ticket 22 load qualification

Run `bun run test:load` from `backend/` with `LOAD_DATABASE_URL` set to a PostgreSQL server URL that can create and drop databases. The harness creates a uniquely named `tt_load_*` database, applies the checked-in migrations, seeds 500 Participants and Tickets, builds and launches the backend as a separate Bun process, drives public HTTP/WebSocket requests from the load process, writes `tests/load/reports/load-qualification.json`, and drops the disposable database in `finally`.

The report records the host CPU, memory, OS, Bun runtime, PostgreSQL version, application pool (20 connections), peak app-pool connections, active queries and PostgreSQL wait events, backend-process peak RSS, and one-second event-loop delay samples (the histogram resets after each sample; the report records the mean of sample means and peak sampled p99/max). Read phases include client wall time from dispatch through parsed response, worker-local fetch/parse time, and server handler time; the unchanged client wall-time percentiles decide pass/fail. The load runner sets Bun's HTTP request cap to 512 so all 500 concurrent clients can be in flight, and dispatches read requests from 10 Bun workers; the report records the cap. It records 500 participant sockets, Draw propagation, request percentiles, and post-load participant state recovery. During sustained concurrency 500, every read must succeed and `/health` must remain available; after that load stops, 500 participant game-state reads and health/readiness checks verify recovery. It verifies 500 distinct Ticket reads, gap-free unique Draw sequences, exact ordered Draw payload delivery to connected Participants, same-key Draw retry idempotency, recovery through participant Draw history after reconnect, and one verified Winner with all remaining eligible Claims rejected after the capped Pattern closes. It also measures a separate five-row participant import against a local fake email provider, outside the live-game read baseline.

Default qualification performs 500 real participant logins in batches of 10, then uses 500 users for the game workload, with 10 seconds of warm-up and 30 seconds of sustained mixed Ticket/current-Round reads at concurrency 500. Set `LOAD_WARMUP_SECONDS=0` and `LOAD_DURATION_SECONDS=1` only for a quick local smoke run; record the exact settings when comparing reports. The acceptance run must use the defaults. It exits nonzero on a read p50 >=200ms, p95 >=500ms, p99 >=1000ms, unexpected HTTP statuses, Draw propagation >=1 second, or an invariant failure. Write-phase percentiles are recorded separately because the PRD latency thresholds target normal read APIs.

The 500 participants use one shared Argon2id test password hash and authenticate through the real login endpoint in batches of 10, so the report includes password verification, rate limiting, Session creation, and cookie issuance without allocating Argon2's full memory cost 500 times at once. The small import sample is separately timed and uses a local fake email provider; it does not represent a 500-row bulk import or an external mail service. This is a single-host qualification and its result depends on the recorded hardware and PostgreSQL setup; it is not a production traffic guarantee.

The hot reads reuse parameterized SQL per database client and recheck current Session, user, profile, Event, Round, and Ticket state on every execution. This stores SQL plans, not authorization or game data. All 500 WebSocket connection attempts are launched together on initial connect and reconnect; the authenticated handshake completes after subscription validation. A public Live Display read runs concurrently with every 500-request sustained Participant batch and has its own latency gate.

On Linux, optional `LOAD_DRIVER_CPUS` and `LOAD_SERVER_CPUS` use `taskset --cpu-list` to separate the load driver and backend scheduling. The OS validates CPU sets and a missing/invalid `taskset` fails the run. The report records actual allowed CPU sets. This local i5-12450H qualification assigns physical P-cores 0–1 (logical CPUs 0–3) to the backend and P-cores 2–3 (logical CPUs 4–7) to the driver; PostgreSQL remains on the same local host. Inspect `lscpu -e=CPU,CORE,SOCKET,ONLINE` before selecting sets for another machine.
